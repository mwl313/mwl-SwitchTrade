# STEP 10 실패 원인 분석 — application_data 바이트 대조 (2026-08-22 밤)

> 실측: 실제 스위치 A(DESTROY) 광고 vs 우리 EMU 방 광고 — 둘 다 122B, ldn-mon 캡처 hexdump 비교

## 1. 발견된 차이 3건

| # | 오프셋 | 스위치(DESTROY) | 우리(EMU) | 분석 |
|---|---|---|---|---|
| **D1** | [21:23] | `01 01` | `00 00` | 미확인 플래그. 스위치는 항상 1로 세팅. **방 검색 필터 조건일 가능성** |
| **D2** | [26:31] | `03 01 'Min'` | 전부 00 | 방장 닉네임 TLV. `[26]=03`(필드ID), `[27]=01`(?), `[28:]='Min'...`. **스위치 프로필 이름** |
| **D3** | RFU partner_info[16:18] | `84 15` | `00 00` | LE u16 = 5508. 용도 불명 (프로필/계정 파생값 추정) |

## 2. 일치하는 것 (문제없음 확인)

| 오프셋 | 값 | 의미 |
|---|---|---|
| [0:4] | `00 5c 16 00` | Pia 헤더 시그니처 |
| [4] | `58` | 타입 바이트 |
| [92:] RFU payload | base85 인코딩 구조 동일 | TID/name/session 정상 디코딩 확인 |

## 3. 판정

**후보 B(RSN 누락)는 배제**: VM2 `iw scan` 상세에서 우리 방에 RSN/WPA IE가 없음이 확인됐지만,
실제 스위치 방도 오픈 모드일 경우 RSN 없이 동작 가능하며, 무엇보다 **스캔 자체가 실패한 게 아니라
스위치의 "FRLG 방 리스트" 필터링에서 걸러지는 것**으로 보임.

**유력 원인은 D1+D2 조합**: 스위치 LDN 클라이언트는 application_data를 파싱할 때:
- offset [21] 또는 [22] 플래그가 1이어야 유효 방으로 인식하거나,
- offset [26+]의 닉네임 TLV를 파싱해 방 목록 UI에 표시하는데 실패하거나

둘 중 하나(또는 둘 다)가 원인일 확률이 높습니다. 특히 D2는 방 목록에 표시되는 "방장 이름"과
직결되므로, 이 필드가 0이면 파싱 오류로 스킵했을 가능성이 큽니다.

## 4. 수정안 (다음 세션)

```python
# frlgsim/beacon.py _OBSERVED_HEADER_FIELDS 업데이트:
_OBSERVED_HEADER_FIELDS = {
    0: b"\x00",
    1: b"\x5c",
    2: b"\x16\x00",
    4: b"\x58",
    # STEP 10 fix: 스위치 실측값 반영
    21: b"\x01\x01",          # D1: 플래그 (용도 불명이나 스위치가 1로 세팅)
    # D2: 닉네임 TLV — nickname을 받아서 동적 생성 필요
    # 26: b"\x03\x01" + nickname_bytes[:N]  ← 정확한 TLV 형식 추가 분석 후
}
```

단, D2의 정확한 형식(TLV 길이 필드 위치, 최대 길이)은 실제 스위치 닉네임이 더 긴 경우의
샘플이 필요합니다. 현재 'Min'(3글자) 샘플만으로는 단정 불가.
