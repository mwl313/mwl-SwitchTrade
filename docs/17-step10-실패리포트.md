## 3. 실패 원인 후보 3건 (우선순위순)

### 후보 A — Vendor Action payload 형식 문제 (유력)
LDN 방 검색은 일반 Beacon 파싱이 아니라 **Vendor Action 프레임의 커스텀 payload**를 해석합니다.
- 실측: 우리 Action 프레임은 나가고 있음(158개/40초), hex에 comm_id도 보임
- 의심 지점: payload 구조가 실제 스위치 것과 미묘하게 다를 가능성
  - T1/T3 때 실제 스위치가 뿌린 Action 프레임 캡처본과 바이트 단위 대조 필요
- 참고: diag 캡처에서 `0100 6fa0 233f 8000` 패턴 확인(우리 comm_id) — 헤더는 맞는 듯하나
  application_data 위치/길이/암호화 여부는 미확인

### 후보 B — RSN(WPA2) IE 누락
- 실제 스위치 LDN 방은 WPA2-PSK(CCMP) 사용. ldn 코드는 wlan_key 유무에 따라 RSN IE를
  START_AP attrs에 포함(`wlan.py:1330`)
- 진단 결과: `security_mode=PROD(1)` + password 64B 정상 → **wlan_key 16B derive 성공 확인**
- 그러나 **실제 공중 비콘에 RSN IE(0x30)이 있는지는 미확인** — 비콘이 mon으로 루프백되지 않아
  직접 확인 불가. VM2 `iw scan` 상세에서도 RSN 라인 미관측(→ 없을 가능성 높음)
- 만약 RSN이 빠졌다면 스위치는 "암호화 없는 이상한 방"으로 필터링했을 것

### 후보 C — hostapd 잔존 충돌
- 크로스체크 과정에서 hostapd(MWLTEST)와 ldn 방이 같은 카드에 공존한 시간이 있었음
- 스캔 결과 오염 가능성. 다음 테스트는 반드시 깨끗한 상태에서

## 4. 추가 관찰

- **ldn.scan hang 재발**: VM2에서 ldn.scan 실행 시 커널 block 의심(SSH 응답 지연). D-1 이슈 재발로 보임 —
  다음 스캔 테스트는 반드시 외부 timeout 워치독(scan_phy.py) 병행할 것
- 8188EU 수신 사망 2회 → authorized 토글로 복구 (예상된 패턴)
- hostapd 대조실험 재확인: hostapd AP(MWLTEST)는 VM2 스캔에서 즉시 발견(-15~-37dBm) —
  무선 경로 자체는 건강함

## 5. 해결 계획 (다음 세션)

| 순서 | 작업 | 스위치 필요? |
|---|---|---|
| 1 | RSN IE 오프라인 분석: `_build_host_beacon_head()` 출력과 hostapd beacon hexdump 대조 — RSN IE 추가 여부 결정 | ❌ |
| 2 | Vendor Action payload 바이트 대조: T1/T3 실측 캡처 vs 우리 Action 프레임 (logs/ 아카이브 활용) | ❌ |
| 3 | 1~2 수정 후 hostapd 완전 제거 상태에서 VM1+VM2만으로 ldn.scan 교차검증 (found ≥1 목표) | ❌ |
| 4 | 위 통과 후 스위치A 재테스트 | ✅ |

## 6. 운영 노트

- ldn.scan 실행 시 외부 timeout 워치독 필수 (D-1 재발 방지)
- hostapd 테스트 후에는 반드시 `pkill hostapd` + 인터페이스 managed 복귀 확인
- 8188EU는 세션 시작 시 먼저 생존 체크(CH1 packets > 5) 후 사용
