## 0. V-1 실측 결과 (2026-08-22, VM1 + 8192EU + rtl8xxxu, 커널 7.0)

### 방법
같은 카드 위에 모니터 vif 2개(vif_tx/vif_rx, 채널 1)를 만들고, vif_tx로 프레임 주입 →
vif_rx에서 tcpdump `-y IEEE802_11_RADIO` 재캡처 → 바이트 단위 대조.

### 실험 1: FCS 자리 0x00000000 (5회 주입)
```
보냄:  ...4d574c563154455354 | 00 00 00 00
받음:  ...4d574c563154455354 | 00 00 00 00   ← 5/5 바이트 완전 일치
```

### 실험 2: 일부러 틀린 FCS `deadbeef` (3회 주입)
```
보냄:  ...1d2263b5 | de ad be ef   (틀린 FCS)
받음:  ...1d2263b5 | de ad be ef   ← 틀린 FCS 그대로 통과, 3/3 동일
```

### 관찰
- 캡처 radiotap: 길이 11B, present `0x01000000` — **FCS-present 비트(0x10) 없음**
- 드라이버(rtl8xxxu)는 모니터 주입 시 FCS를 계산·덧붙이지 않음 — 넣은 바이트 그대로 송출
- PACKET_IGNORE_OUTGOING 에러 없음 (커널 7.0 지원)

### 판정
| 질문 | 답 |
|---|---|
| 주입↔재캡처 바이트 동일? | ✅ 완전 동일 (FCS 포함 8/8회) |
| 드라이버 FCS 덮어쓰기? | ❌ 없음 |
| EchoGuard 루프 리스크(C-1)? | ✅ 이 환경에서는 발생하지 않음 |

→ **시나리오 A 확정**: 현행 sha1 방식 유지. STEP 6(EchoGuard 재구현) 불필요.

### 유의점
1. 이 결과는 rtl8xxxu+8192EU+커널 7.0 조합 기준. 카드/커널 변경 시 V-1 재실행 필수(docs/13 하단 체크리스트).
2. "틀린 FCS가 공중으로 나간다"는 점은 수신자가 FCS 검증 실패 시 폐기할 수 있음을 의미.
   실전 LDN 경로(frldn/TAP 주입)에서는 T1~T4 실측 성공이 이미 있어 실무상 문제 없었으나,
   framerelay E2E(V-4) 때 주입 프레임의 FCS 처리를 한 번 더 관찰할 것.

## 1. 배경 — C-1 요약

EchoGuard(`framerelay/bridge.py:99-131`)는 "주입한 프레임 == 재캡처된 프레임"을 sha1
전체-바이트 비교로 가정한다:

- 주입 시 `record(payload)` → 캡처 시 `duplicate(frame)` → 해시 일치면 폐기 (루프 방지)
- `PACKET_IGNORE_OUTGOING` 미지원 커널(<4.20)에서는 이것이 루프 방지의 **유일한 방어선**

그런데 드라이버가 (a) FCS를 덧붙이거나, (b) radiotap/헤더 패딩을 넣으면 재캡처 바이트가
달라져 해시가 어긋나고, 미스매치 1회부터 **양단 무한 ping-pong 증폭 루프**가 시작된다
(docs/10 C-1). `strip_radiotap`(`framerelay/radio.py:64-75`)은 길이로만 자르고 radiotap
Flags(present bit `0x10`)의 FCS 포함 표시를 폐기하므로 현재로선 구분 불가.

V-1: 카드 A 주입 → 모니터 재캡처 hexdump 대조 (tcpdump `-y IEEE802_11_RADIO`)로 어느
시나리오인지 판정한다. 아래 §2 절차.

## 2. V-1 판정 절차 — A/B/C 가르기

카드 1개, 스위치 불필요 (docs/10 §실기검증 V-1).

1. 모니터 인터페이스에서 tcpdump 캡처 시작: `tcpdump -i <mon> -y IEEE802_11_RADIO -XX`
2. 브리지 또는 수동 스크립트로 임의 프레임 주입 (`wrap_radiotap` 8B TX 헤더 + bare frame)
3. 주입한 bare frame 바이트와 재캡처에서 radiotap 헤더를 벗긴 802.11 프레임을 hexdump 대조

| 관찰 | 판정 |
|---|---|
| 길이 동일, 바이트 완전 일치 | **시나리오 A** |
| 재캡처가 정확히 +4B이고 꼬리 4B가 CRC32(FCS), 본체는 일치 | **시나리오 B** |
| 길이 차이 ≠ ±4, 또는 802.11 헤더 영역 자체 변형/패딩 삽입 | **시나리오 C** |

radiotap Flags(present bit `0x10`)가 FCS 부착 여부를 알려주므로, 캡처 덤프에서 present
비트맵도 함께 기록해두면 B/C 구분과 구현 검증에 도움이 된다.

## 3. 시나리오 A: 바이트 완전 일치 확인됨 → 현행 유지 (변경 없음)

**판정 내용**: 드라이버가 FCS를 붙이지 않고, 패딩 변형도 없다. 재캡처 == 주입 바이트.

**설계**: 변경 없음. `sha1(frame)` 전체 해시 유지 (`bridge.py` record/duplicate 그대로).

- 근거 확보 상태가 된다: `MonitorRadio.open()`의 PACKET_IGNORE_OUTGOING 세팅
  (`radio.py:149`) + 드라이버 무-FCS → EchoGuard 전제가 실측으로 참 입증.
- 단, 이 전제는 **환경 속성**이다: 카드 교체(8192EU↔8188EU), 커널 업데이트, 드라이버
  버전 변경 시 재소멸할 수 있다 → V-1을 카드/커널 변경 시마다 재실행하는 체크리스트 항목으로
  등록할 것 (docs/07 §7 계열).

**리스크**: 환경이 바뀌면 전제가 조용히 무효화됨(코드는 그 사실을 모름). 완화 = 위 재검증
체크리스트 + 아래 §7 공통 안전망(항상 적용).

**구현 난이도**: 없음.

## 4. 시나리오 B: FCS 4B 차이만 있음 → radiotap Flags 파싱 + `frame[:-4]` 해시

**판정 내용**: 재캡처가 주입 프레임 + 꼬리 4B(FCS). 본체 바이트는 일치.

**설계 (두 겹):**

1. **`strip_radiotap` 개선** (`framerelay/radio.py`):
   - radiotap 헤더를 순서대로 워크하는 파서 추가: present 비트맵(오프셋 4, u32 LE)을 읽고,
     radiotap 표준 필드 순서대로 각 present 비트의 필드 크기만큼 전진하며 **Flags 필드
     (present bit `0x10`, u8)** 를 추출. Flags 위치는 앞선 present 비트 구성에 따라 달라지므로
     순차 워크가 필요하다 (대략 25~30줄).
   - `flags & 0x10` (FCS at end) 설정 시 프레임 꼬리 4B 절단 후 반환. 미설정/파싱 불가 시
     현행과 동일하게 원본 반환 (**fail-open**: 파서 결함이 중계 투명성을 깨는 일이 없게).
2. **EchoGuard 해시 정규화**: `record()`/`duplicate()` 양쪽 모두 `sha1(frame[:-4])` 기준.
   - 방어적 이중 절단 — strip_radiotap이 FCS를 못 잘라주는 드라이버 변종(플래그 미설정+
     무음 FCS 부착)까지 흡수. 양측이 동일 절단을 적용하므로 일관성 유지.
   - 길이 4B 미만 프레임은 원본 그대로 해시.
   - `BeaconCache.add`(`bridge.py:78`)에도 동일 정규화 적용 권장 — 아니면 FCS 유무만 다른
     동일 비콘이 캐시 중복 엔트리를 만든다(루프는 아니지만 capacity 4 낭비).

**리스크**: radiotap 파서 오류 시 (a) fail-open이라 루프 위험은 없으나 (b) EchoGuard가
무력화될 수 있음 → §7 안전망이 받는다. 파서 단위 테스트로 실측 RX 헤더 샘플 고정.

**구현 난이도**: 하~중. (~30줄 파서 + 해시 컷 + 테스트)

## 5. 시나리오 C: padding/변형 불가피 → 식별 튜플 키 전환

**판정 내용**: FCS 외에 드라이버별 헤더 패딩 등 변형이 있어 "정규화로 원본 복원"이
불가능/취약하다. 바이트 해시 자체를 포기하고 **변형에 내성 있는 논리 키**로 전환.

**설계:**

- 해시 키를 튜플로: `(type, subtype, addr1, addr2, addr3, seq_ctrl)`
  - `seq_ctrl`: 802.11 헤더 offset 22–23, u16 LE (상위 12bit sequence number, 하위 4bit
    fragment number). 송신자별 순차 증가 → **재전송(retry)까지 포함해 "동일 프레임" 식별용**.
    retry bit는 FC 영역(frame[1] bit3)이라 키에 안 들감 — 재전송본도 같은 키로 매칭됨.
  - addr은 raw 6바이트. `parse_80211`(`radio.py:83`)에 seq_ctrl 추출 확장(Dot11 namedtuple
    필드 추가, framerelay 전용이라 Track A 영향 없음).
- 폴백: 24B 미만 헤더(control 프레임 등 seq_ctrl 부재) → `(type, subtype, addr1)` + 길이
  러프 키, 또는 raw sha1 병행. ACK 루프는 PACKET_IGNORE_OUTGOING/커널이 이미 1차 방어.
- `_seen` 저장소는 dict[튜플→timestamp] 그대로, prune 로직(M-1 수정분) 재사용.

**리스크 (정직하게):**

- **위음성 억제**: ECHO_WINDOW(2s) 내 우리 스위치의 *정상* 재전송이 같은 키로 폐기된다.
  원본은 이미 중계됐으므로 손실은 "재시도 1회분" — 무한 증폭 루프 대비 수용 가능. 민감하면
  window 단축(2s→0.5s)으로 완화. 비콘 재생(BeaconReplayer)도 record()를 거치므로 영향 없음
  (재생 자체가 의도적 반복).
- **충돌 가능성**: 서로 다른 프레임이 같은 키를 가지려면 같은 송신자가 2s 창 안에 같은
  sequence 번호를 재사용해야 함 — 4096 시퀀스 순환 주기가 창보다 수 배 크므로 사실상 없음.
- 해시 강도 상실은 문제없다: EchoGuard는 "우리가 방금 넣은 것" 식별이 목적이고, 공격자
  모델이 아니다.

**구현 난이도**: 중. (~50줄: parse 확장 + 키 생성 + 폴백 정책 + 테스트)

## 6. 시나리오 비교표

| 항목 | A: 현행 유지 | B: FCS 절단 | C: 튜플 키 |
|---|---|---|---|
| 전제 | 재캡처 == 주입 바이트 (실측 확인) | 차이가 FCS 4B뿐 | padding 등 변형 불가피 |
| 코드 변경 | 없음 | strip_radiotap 파서 + `frame[:-4]` | parse_80211 확장 + 키 전환 |
| 장점 | 제로 리그레션, 검증만으로 완결 | 바이트 해시 강도 유지, 투명 중계 유지 | 어떤 바이트 변형에도 내성, retry까지 식별 |
| 단점/리스크 | 카드/커널 변경 시 전제 소멸(재검증 필요) | 파서 버그 시 EchoGuard 무력화(fail-open이라 루프는 아님) | 정상 retry 위음성 억제, 충돌 이론 여지, 구현 면적 최대 |
| 구현 난이도 | 없음 | 하~중 (~30줄+테스트) | 중 (~50줄+정책+테스트) |
| 검증 방법 | V-1 | V-1 + radiotap Flags 덤프 대조 | V-1 + retry 프레임 실측(V-4 연계) |

**선택 규칙**: V-1 결과가 A면 A로 종료. B와 C의 경계(패딩 존재 여부)가 애매하면 B를 먼저
적용해보고 재캡처 대조가 여전히 어긋나면 C로 승격 — B는 C의 부분집합처럼 출발 가능하도록
절단 로직을 독립 함수로 유지할 것.

## 7. 공통 안전망: 초당 중계 상한 (rate limiter)

어떤 시나리오를 선택하든, 로직 버그·미지 드라이버 변형·미래 회귀로 루프가 시작되는 순간을
**물리적으로** 막는 최후 방어. EchoGuard가 "논리적" 방어라면 이것은 "정량적" 방어다.

- **근거 수치**: 정상 최대 부하 ≈ 비콘 재생 4개×10Hz=40/s(docs/10 M-4) + 데이터 교환 수십/s
  → 여유 5배. 루프 폭주는 양단 증폭으로 수천 frames/s에 도달. → **기본 상한 200 frames/s**,
  초과 시 경고+drop.
- **구현**: `framerelay/rate_limit.py` `TokenBucket` (이번 커밋, 클래스+테스트만 선행).
  - TokenBucket 선택 이유: O(1) 메모리(공격 중 타임스탬프 deque 성장 없음), burst 파라미터가
    정상 마이크로버스트(재생 틱의 4연발 등)를 자연 흡수.
  - `allow(frame_len)->bool` — 초과 시 False. frame_len은 게이트가 아니라 통계 누적용.
  - drop 발생 시 경고 로그를 **1s 스로틀**로 출력 — 폭주 중 경고 홍수가 디버깅을 더 망치지
    않게 한다 ("경고+drop"의 경고도 상한을 갖는다).
  - **주입 가능한 clock** 파라미터 → time.sleep 없는 결정론 오프라인 테스트
    (`tests/test_rate_limit.py`).
- **적용 지점(구현 시)**: 최소 `on_ws_message` 주입 직전(공중을 실제로 때리는 쪽), 권고는
  capture→relay 방향까지 양측. stats에 dropped 노출 → `--verbose`/종료 요약 반영.
- **현재 상태**: bridge.py 미적용 — 시나리오 확정 후 STEP 6(D-1)에서 함께 연결한다.
  (docs/12 STEP 4 범위 준수)
