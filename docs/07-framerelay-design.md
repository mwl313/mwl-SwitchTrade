# 07 — B안 (리더-조인 프레임 중계) 상세 설계

> 작성: 2026-08-21 | 상태: [확정] 설계 v1 (주인님 승인)
> 포크 세션 전용 — 자연스러운 양방향 직접 통신 (서로의 이름이 보이는 방식)

## 1. [확정] 목표 & 방식

```
스위치 A(리더) ←무선→ 브리지 A ←WSS→ 릴레이 ←WSS→ 브리지 B ←무선→ 스위치 B(참가자)
```

- 양쪽 스위치는 **실제 로컬 무선 트레이드와 100% 동일**하게 동작
- 스위치 A 화면: "B 닉네임 님이 참가했습니다" / 스위치 B 화면: "A 닉네임의 방"
- 브리지는 **투명 중계기** — 프레임을 해석하지 않고 통째로 양방향 전달
- **게임 해석(frlgsim) 불필요** → 트랙 A(emu/)와 완전 독립

## 2. [확정] 핵심 원칙 — 투명 중계 (count 패치 폐기)

### 왜 count 패치가 폐기됐나 (재검토 2026-08-21)

| 전제 (구안) | 실제 동작 | 결과 |
|---|---|---|
| 브리지 A가 스위치 A에 참가자로 join → 세션 2/2 | 스위치 A 광고 = 2/2 | ✅ 직접 연결 방지 |
| 브리지 B가 광고를 1/2로 패치 재생 | 스위치 B: "자리 있네" → 조인 | — |
| 조인 요청이 스위치 A에 도달 | 스위치 A: "이미 2/2" → **거부** | 💥 게임 꼬임 |

**결론**: 광고만 속이고 실제 세션은 가득 차 있으면 조인이 거부된다. 패치는 오히려 꼬임 유발.

### 정답 구조 (채택)

```
스위치 A: 혼자 방을 열고 광고 (자연 상태 = 1/2) ← 조작 없음
브리지 A: 캡처 + 주입만 (스위치 A 광고/응답을 릴레이로 전달)
브리지 B: 재생 + 캡처만 (스위치 B에게 광고 보여주고, B의 요청을 전달)
스위치 B: 실제 스위치 A 방 발견 → 정상 조인 (자기 MAC 그대로)
```

- 광고가 자연히 1/2 → **패치 불필요**
- 스위치 B 조인 요청(SA=스위치 B MAC)이 그대로 스위치 A에 도달 → 정상 수락
- 암호화: 스위치 A↔B가 직접 핸드셰이크, 브리지는 복호화 불필요 (프레임 통째 중계)

## 3. [확정] 실측으로 검증된 전제 조건

| 항목 | 결과 | 근거 |
|---|---|---|
| 모니터 모드 RX | ✅ 2카드 모두 | phy6 0.94s / phy7 1.32s 스캔 정상 |
| 모니터 모드 TX | ✅ radiotap 헤더 포함 시 성공 | 8/21 실측: 양방향 20/20 + AP Probe Response 응답 |
| **radiotap 헤더 필수** | ✅ 8바이트 `00 00 08 00 00 00 00 00` | 헤더 없이 send하면 드라이버가 조용히 버림 (실측) |
| 카드 구분 | ✅ MAC 주소 | A=`00:ad:a7:11:73:09` (8188EU), B=`a0:47:d7:b0:2b:39` (8192EU) |
| 릴레이 서버 | ✅ 공용 `relay/server.py` | bytes 파이프, 테스트 4개 통과 |
| 스위치 광고 캡처 | ✅ | 8/20 실측: comm_id 디코드 + DESTROY 비콘 |

## 4. [확정] 남은 리스크 — 802.11 ACK/타이밍 (실측 대상)

| 항목 | 내용 |
|---|---|
| 무선 규칙 | 유니캐스트 수신 후 **SIFS(수 μs) 안에 ACK** 필요 |
| 우리 구조 | ACK도 인터넷 왕복(50~200ms) → 스위치 재전송 폭주 가능 |
| 영향 | 조인/데이터 단계에서 "연결 불안정" 처리 가능 |
| 대응 | 스위치 2대 실측 → 막히면: 관리 프레임만 중계 + 데이터는 Pia 레벨 우회 검토 |

## 5. [확정] 테스트 환경 — 물리 분리 구성 (케이블 방식)

```
[방 안]                                  [방 밖 (문 너머)]
Switch A(리더)                           Switch B(참가자)
브리지 PC (Windows + VMware VM + 카드A)    카드 B ← USB 2.0 연장 10m (리피터 내장)
```

- **USB 연장 10m** (리피터 내장, 구매 완료) — 카드 B만 방 밖으로
- 문을 닫으면 스위치 A 실제 광고가 B에 도달 불가 → **직접 연결 원천 차단**
- 검증: 방 밖 카드 B 스캔 → 실제 A 광고 0개 확인
- 프로덕션: 원격이면 자동 분리 — 이 구성은 테스트 전용

## 6. [방향] framerelay/ 구현 스펙 (케이블 도착 후 오픈코드 위임)

```
framerelay/
├── radio.py    # 모니터 캡처/주입
│   ├── 캡처: AF_PACKET raw (모니터 iface) → 802.11 프레임 (radiotap 제거)
│   ├── 주입: radiotap 8B 헤더 추가 → send (실측 필수 사항)
│   └── 필터: 호스트 MAC(BSSID) 기준 — 자기 스위치만 중계
├── bridge.py   # 중계 루프
│   ├── radio 캡처 → MWLB 프레임(0x20 FRAME_RELAY) → WS 릴레이
│   ├── WS 수신 → radio 주입
│   └── heartbeat 30s + 재연결 3회 (릴레이 API 재사용)
└── common/mwlb.py  # MWLB 코덱 공용 추출 (트랙 A와 공유)
```

- 릴레이: `relay/server.py` 그대로 사용 (bytes 파이프 = 프레임 중계에 적합)
- MWLB 메시지 타입 추가: `0x20 FRAME_RELAY` (payload = raw 802.11 frame)
- 광고(비콘)는 **주기 재생 스레드** 필요 (100ms 주기 실측 후 조정)

## 7. [확정] 테스트 절차 (케이블 도착 후)

```
1. 방 안/밖 분리 구성 + 문 닫기
2. 방 밖 카드 B 스캔 → 실제 A 광고 0개 (분리 검증) ✅
3. 브리지 A가 스위치 A 광고 캡처 → 릴레이 → 브리지 B 재생
4. 스위치 B(참가자) 화면에 "A의 방" 표시 확인 ← B안 첫 성공 기준
5. 조인 → 어디서 막히는지 관찰 (ACK 리스크 발생 지점)
6. 세션 성립 → 트레이드 진행 (양쪽 화면에 실제 닉네임 확인)
```
