## 1. 전제 정리 — 용어 충돌 해소 (논의 시 혼동 방지용)

프로젝트에서 "host"가 두 곳에서 다른 의미로 쓰인다. ChatGPT 논의 전에 이 구분을 먼저 공유할 것.

| 용어 | 정체 | 쓰이는 곳 |
|---|---|---|
| 릴레이 역할 host/guest | 파이프 슬롯 라벨 — "스위치 A(리더) 옆 브리지" vs "스위치 B 옆 브리지" | framerelay CLI `--role host` |
| **브리지 호스트 모드** | 브리지 자신이 LDN 방을 직접 만들어 공중에 뿌리는 기능 (스위치가 검색해서 조인) | STEP 8 개발 중 |

### 두 모드의 그림

```
【베이스 모드】 (v0.1 목표 — 이 문서의 기준)
스위치 A가 리더로 방 개설 → 브리지A 캡처→릴레이→브리지B 재주입 → 스위치B가 "속아 보이는" 방에 조인
주인: 스위치 A · 브리지는 투명 중계기

【브리지 호스트 모드】 (v0.2 보류 — STEP 8)
브리지A가 자체적으로 방을 합성·브로드캐스트(AP+RFU비콘) → 스위치 A도 검색해서 조인
주인: 브리지 · 양쪽 모두 "조인하는 쪽"이 되어 흐름 대칭화
현황: 방 개설 + RFU 비콘 인코더 실측 성공 / 비콘 공중 관측 미확인
      (원인 확정: ldn BEACON_HEAD의 SSID/rates IE 누락 — hostapd 크로스체크 완료, 보강 패치 대기)
```

### v0.1에서 사라지는 제약

베이스 모드에선 양쪽 브리지 모두 "모니터 수신 + 주입"만 필요하다.
→ **8188EU든 8192EU든 방 만들기·참가하기 둘 다 가능** (카드 매트릭스의 HOST=8192EU 제한은 브리지 호스트 모드 기준).
→ v0.1 UI에 하드웨어 게이트 없음.

## 2. 핵심 인사이트 — "방"이 두 개다 (clunky함의 근원)

| | 릴레이 방 (로비) | 무선 세션 (LDN) |
|---|---|---|
| 실체 | 서버 위의 모임 공간 (코드·제목·상태) | 스위치 리더가 실제로 열어둔 게임 방 |
| 생성 시점 | 앱 클릭 즉시 | **스위치를 리더 대기에 둔 후에만** |
| 닉네임·인원 등 게임 정보 | 없음 (유저 입력만) | 있음 (RFU 비콘 application_data에서 읽힘) |

공방 리스트 딜레마("게임 정보는 스위치 연결 후에만 보인다")는 이 둘을 한 개의 방으로 뭉뚱그린 데서 온다.

## 3. [승인] 방 생성 타이밍: 하이브리드 (옵션 C)

### 검토했던 3개 옵션

| | ① 스위치 연결 후 방 생성 | ② 방 먼저, 페어링은 내부 | **③ 하이브리드 (채택)** |
|---|---|---|---|
| 흐름 | 클릭 → 스위치 리더 대기 → 페어링 → 그제야 방 존재 | 클릭 즉시 방 → 초대 → 준비되면 함께 스위치 조작 | ② + 상태 정직 노출 |
| 장점 | 리스트 정보가 항상 진짜, 유령방 없음 | 소셜 UX 자연스러움, 비동기 합류 가능 | ② 경험 + ① 정직함 |
| 단점 | 비동기 붕괴 — 초대하려면 먼저 스위치 앞 착석, 리스트 늘 텅 빔 | 유령 방 위험 ("들어왔는데 아무 일도 없음") | 구현 약간 증가 (상태 배지) |

### 채택 설계 — 규칙 3개

1. **방 만들기 클릭 = 릴레이 방 즉시 생성.** 코드 발급·공유·QR은 그 순간부터. 스위치 꺼져 있어도 방은 살아있음.
2. **무선 세션은 별도 상태로 추적**: `로비` → `페어링 중` → `교환 중`. 양쪽 다 "준비" 누르면 **양쪽 동시 가이드** 표시
   (호스트: "스위치를 리더 대기로" / 게스트: "검색 화면을 열어두세요") → 비콘 감지 시 자동 진행.
3. **공방 리스트에 상태 배지**: 조인 버튼은 페어링 완료 방만 활성. 미완료 방은 회색 "스위치 대기 중". 유령방 클릭 차단.

### 리스트 필드의 상태별 채움

| 필드 | 페어링 전 | 페어링 후 |
|---|---|---|
| 방 제목 | 유저 입력값 ✅ | 동일 |
| 방장 닉네임 | 앱 등록 닉네임 (없으면 "—") | **게임 닉네임으로 교체** (RFU 비콘 디코드 — 실측 완료) |
| 인원 | 로비 인원 | 게임 세션 인원 |
| 신호강도 | 브리지↔릴레이 RTT ✅ 항상 측정 가능 | 동일 |
| 거주 지역 | GeoIP ✅ 항상 가능 | 동일 |
| 배지 | 🟡 스위치 대기 중 | 🟢 교환 가능 |

## 4. [승인] 통신 구조 — 브리지는 양방향 파이프

"호스트가 리더로 방 파놓음 → 브리지 감지 → 릴레이"는 **하행 절반만** 맞고, 실제 코드(`bridge.py`)는 양방향:

```
[스위치 A] ⇅무선⇅ [브리지A: 캡처+주입] ⇄MWLB⇄ [릴레이] ⇄MWLB⇄ [브리지B: 캡처+주입] ⇅무선⇅ [스위치 B]
```

| 브리지 기능 | 방향 | 내용 |
|---|---|---|
| 캡처 | 공중→릴레이 | 내 스위치 프레임(비콘·조인·데이터)을 MWLB 0x20 포장 전송 |
| 주입 | 릴레이→공중 | 상대 프레임을 radiotap 8B 헤더 붙여 재발사 |
| 비콘 리플레이 | 릴레이→공중 100ms | 스캔 중 상대 스위치가 방을 계속 보이게 캐시 비콘 반복 주입 |
| 에코 차단(EchoGuard) | 내부 | 자기 주입 프레임 재캡처 → 무한 ping-pong 방지 |

## 5. [승인] HOST 유저 플로우 (v0.1 베이스 모드)

```
[앱] 방 만들기 → {공방 | 코드방} 선택 → 릴레이 세션 등록 → 6자리 코드 발급
  → 🟢 로비 화면: 코드/QR 공유 (상대 접속 대기 — 스위치 아직 안 켜도 됨)
[유저 or 상대 접속 후] "준비" 버튼
  → 🔵 페어링 가이드: "스위치에서 디렉트 코너 → 교환 → 리더 진입"
[앱] 스위치 비콘 자동 감지 (MAC 자동수집 — 사용자 입력 없음)
  → 🟢 "내 방이 공중에 살아있어요"
      ↓ 상대 브리지 접속
[앱] 🔵 "참가자 접속!"
      ↓ 상대 스위치 조인 프레임 유입 → 내 동글에서 발사
[큐] "스위치 화면에 참가 요청 — 승인해주세요" (리더 승인/거절 절차: EMU 실측 확인됨)
[유저] 스위치에서 승인
      ↓
[교환중] 계기판 (프레임 흐름·RTT·연결 건강도) — 여러 마리 순차 교환 가능
[완료]
```

## 6. [승인] GUEST 유저 플로우

매직 모먼트 = **내 스위치 방 리스트에 멀리 있는 방이 속아 나타나는 순간**.

```
[앱] 참가하기 → 코드 입력 (or 공방 리스트 선택)
  → 릴레이 연결 → 🟢 "연결됨 — 상대방 방을 찾는 중…"
[큐 ①] "스위치에서 방 검색 화면을 열어두세요"
[유저] 스위치: 디렉트 코너 → 교환 → 참가(검색)
[앱] 호스트 비콘 수신 → 100ms 주기 재주입 (BeaconReplayer)
  → 📡 "상대방 방을 내 근처에 비추고 있어요"
[큐 ②] ⭐ "스위치 방 리스트에 '○○님의 방'이 보이면 선택해 입장하세요"
[유저] 방 선택 → 조인 (조인 프레임: 내 스위치→캡처→릴레이→호스트 브리지 주입→호스트 스위치)
[호스트] 스위치에서 승인
      ↓
[같은 방 두 명] → 교환 진행
[완료]
```

## 7. [제안] 실패 지점별 큐 (UI 필수 분기)

| 상황 | 감지 신호 | 큐 문안 | 해결 버튼 |
|---|---|---|---|
| 게스트 스캔에 방 안 뜸 | 비콘 주입 카운터 0 / 릴레이 수신 없음 | "동글이 잠깐 멈췄어요" | [복구] (usbipd detach/attach 사이클) |
| 조인했는데 승인 없음 | 조인 재전송 프레임 반복 관측 | "상대가 스위치에서 승인해야 해요" | 알림 전달 only |
| 교환 중 끊김 | 프레임 흐름 정지 + WS heartbeat | "연결이 불안정해요" | [재접속] |
| 호스트 스위치 미감지 | 비콘 타임아웃 | "스위치가 리더 대기인지 확인해주세요" | [다시 감지] |

## 8. UI 상태 머신 요약 (화면 체계의 뼈대)

```
HOST : 로비 → 페어링가이드 → 비콘확인 → 대기(참가자접속) → 승인대기 → 교환중 → 완료
GUEST: 코드입력 → 페어링가이드 → 비콘주입중 → 방선택대기(유저행동) → 승인대기 → 교환중 → 완료
```

각 상태에 붙는 것:
- ① 한 문장 안내
- ② **행동 주체 표시** (🤖 앱 자동 / 🎮 스위치 조작 / 👥 상대방 대기) — 색+아이콘 구분
- ③ 타임아웃 분기 → §7 큐

컴맹 원칙(docs/17 §4)과 결합: 전문용어 금지 / 메인 버튼 2개 / 에러=문장+해결버튼 1개 / 고급은 서랍 / 상태는 색.

## 10. ChatGPT 디자인 논의용 브리핑 포인트 (다음 세션에서 전달할 것)

1. 제품 한 줄: "순정 닌텐도 스위치의 GB 포켓몬 교환을 인터넷으로 중계하는 PC 유틸리티 — 사용자는 '연결 도우미'만 경험"
2. 사용자 2종: HOST(방 만드는 사람)/GUEST(참가하는 사람), 조작은 스위치 게임 화면에서 이루어짐
3. 기술 제약: Windows exe(PyInstaller+pywebview/WebView2), WSL2 완전 은닉, 백엔드 Python
4. 확정된 UX 원칙: docs/17 §4 컴맹 5원칙 + 이 문서 §8 상태머신
5. 확정된 데이터: 공방 리스트 5필드(docs/17 §3) + 상태 배지(§3)
6. 물어볼 것: 톤&매너(Q4 밝은 오리지널안 검토), 첫실행 마법사 카피, 매직모먼트(비콘이 속아 나오는 순간)의 연출, 에러 카피 톤, 다크모드 필요성
7. 산출물 요청: 화면별 와이어프레임/카피라이팅 초안 — HTML/CSS 목업으로 이식 가능한 형태
