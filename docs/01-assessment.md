# MWL-SwitchTrade — 기술 Assessment (v0.1)

> 목표: 순정 Switch의 NSO Game Boy 포켓몬(FRLG) 트레이딩을 인터넷으로.
> 이 문서는 기존 기술스택을 레이어별로 평가하고, 조합 방안과 미싱 링크를 정의한다.

---

## 1. 레이어 분해

목표 시스템은 4개 레이어로 분해된다:

```
┌─────────────────────────────────────────────────────────────┐
│ L4. 클라이언트/매칭     세션 ID 생성·공유, 방 참가, 포켓몬 관리 │
├─────────────────────────────────────────────────────────────┤
│ L3. 인터넷 전송        PC 브리지 간 터널/릴레이 (NAT 통과)     │
├─────────────────────────────────────────────────────────────┤
│ L2. 게임 프로토콜      FRLG RFU(무선 어댑터) 시뮬레이션        │
├─────────────────────────────────────────────────────────────┤
│ L1. LDN 링크          Wi-Fi 카드 ↔ Switch 로컬 무선 통신      │
└─────────────────────────────────────────────────────────────┘
```

**핵심 통찰**: L1과 L2는 이미 존재하고 검증됐다. L3이 **미싱 링크의 핵심**이고, L4는 Celio 패턴으로 재사용 가능하다.

## 2. 레이어별 기술 평가

### L1. LDN 링크 — ✅ 기존 기술 (kinnay/LDN)

| 항목 | 평가 |
|---|---|
| 정체 | Python 패키지 (`pip install ldn`), 2022년부터 성숙. 스캔/참가/**호스트** 지원 |
| 동작 방식 | AP 모드(관리 프레임) + 모니터 모드(데이터 프레임) 조합 → 복호화 → TAP 인터페이스 주입 |
| 요구 권한 | `CAP_NET_ADMIN` (sudo), NetworkManager 중지 → **사용 중 인터넷 불가** (유선 연결 시 생략 가능) |
| 한계 | Wi-Fi 카드 의존성 큼 (Intel AX200 등 일부 카드 동작 불가), Linux 전용 |
| **우리 활용** | 브리지 PC가 LDN 네트워크 **호스트**가 되어 Switch가 참가하거나, frlg-ldn-trade처럼 참가자로 동작 |

### L2. 게임 프로토콜 — ⚠️ PoC (tornadus/frlg-ldn-trade)

| 항목 | 평가 |
|---|---|
| 정체 | frlgsim 패키지 — FRLG의 GBA 링크 케이블/RFU 무선 프로토콜을 PC에서 시뮬레이션. 게임이 PC를 "진짜 GBA"로 인식 |
| 검증됨 | 무개조 Switch 2의 NSO FRLG와 실제 트레이드 성공 (2026-06, 영상 데모) |
| 주요 모듈 | `rfu.py`(무선 어댑터), `linkplayer.py`(링크 플레이어 상태), `trade.py`(트레이드), `transport.py`, `pia_connect.py`, `reliable.py` |
| 한계 | ① 연결 재시도 필요, 트레이드 취소 버그 ② 단일 방향 데모 중심 ③ 배틀 미구현 ④ **GitHub 이슈 1건, 개발자 1인+커뮤니티** |
| **우리 활용** | L3과 결합하기 위해 **트랜스포트 계층 교체/확장** 필요 — 현재는 로컬 LDN 위에서 직접 동작하므로, 패킷을 인터넷으로 실어나르는 지점을 추가 |

### L3. 인터넷 전송 — ❌ 신규 (미싱 링크)

| 요구 기능 | 설명 |
|---|---|
| PC↔PC 터널 | 브리지 A↔B 간 신뢰성 있는 패킷 전달 (WebSocket/Socket.IO or QUIC/UDP) |
| NAT 통과 | 홈 네트워크 환경 — 릴레이 서버 경유로 해결 (Celio-Server 패턴: 순수 중계, 게임 데이터 해석 안 함) |
| 세션 관리 | 세션 ID 생성, 참가, 라이프사이클 (둘 다 퇴장 시 삭제), 재연결 타이밍 |
| 지연 예산 | 턴제 게임 특성상 **레이턴시 민감도 낮음** (영상에서 확인: "turn-based helps a lot") — TCP/WebSocket으로 충분 |

**설계 시안**: Celio-Server(Socket.IO, Node.js)를 LDN/RFU 패킷 릴레이로 확장. 서버는 순수 릴레이 (패킷 내용 해석 안 함) — 검증·확장성·법적 리스크 모두 유리.

### L4. 클라이언트/매칭 — ⚠️ 재사용 가능 (Celio-Client 패턴)

- Celio-Client (Angular, WebUSB/WebSerial)의 세션 생성/참가 UI 패턴을 참고.
- 우리의 클라이언트는 WebUSB 대신 **로컬 브리지 데몬**과 통신 (localhost API) — 브라우저가 직접 하드웨어를 만질 필요 없음.
- 단순화: CLI 우선 → 웹 UI는 후순위. (주인님 환경: Windows가 메인 머신이므로 Windows 클라이언트가 실사용에 중요)

## 3. 툴체인 조합 (제안)

```
[Switch (순정 NSO FRLG)]
        │  로컬 무선 (LDN)
        ▼
[PC 브리지 A — Linux]
  ├─ kinnay/LDN        (L1: Wi-Fi 카드 ↔ Switch)
  ├─ frlgsim 확장판     (L2: RFU 시뮬레이션, .pk3 처리)
  └─ bridge 데몬 (신규)  (L3 클라이언트: 터널 연결, 패킷 직렬화)
        │  WSS/QUIC
        ▼
[릴레이/매칭 서버 (신규)]  ← Celio-Server 확장 (Node.js or Go)
        │
        ▼
[PC 브리지 B] ⇄ [Switch B (순정 NSO FRLG)]
```

**핵심 설계 결정**:
1. **게임 패킷은 브리지에서 "캡처 → 직렬화 → 릴레이"** — LDN 무선 프레임을 그대로 보내는 것보다, 게임 프로토콜 레벨(RFU)에서 중계하는 것이 지연·신뢰성·디버깅 모두 유리. frlgsim이 이미 게임 레벨에서 동작하므로 이 경로가 자연스러움.
2. **서버는 무상태 릴레이** — 세션 ID만 알고, 게임 데이터는 모름. (Celio-Server 설계와 동일)
3. **재연결 처리** — 게임 링크 단계(링크 스탠바이 등)에서의 타임아웃/재시도 로직을 브리지가 담당.

| M2 | **frlgsim 트랜스포트 분리** | 로컬 LDN 의존에서 벗어나 원격 피어로 패킷 라우팅 가능하도록 확장 | 중 |

| M6 | **prod.keys 의존성 검증** | README상 필수로 명시. LDN 통신에 실제로 필요한지, 순정 유지와 충돌하지 않는지 리서치 필요 | 리서치 |

## 6. 검증해야 할 열린 질문 (Open Questions)

1. **NSO GB 앱의 FRLG가 어떤 통신 모드를 노출하는가?** — RFU(무선 어댑터)로 확인됨 (frlgsim이 RFU 시뮬레이션). 정확한 모드/파라미터는 frlgsim 소스에서 확인 필요.
2. **prod.keys가 정말 LDN 통신에 필요한가?** — 순정 유지 원칙과의 충돌 여부. Lockpick류 홈브류 없이 얻을 수 있는 경로가 있는지 (예: Switch 2의 공식 키 관련). **아니면 LDN 프레임 암호화에 필요한지** — kinnay/LDN 문서 확인.
3. **Switch 2의 LDN 구현 차이?** — 영상에서 Switch 2에서도 성공. 두 Switch 간 (Switch + Switch 2) 크로스도 가능한지.
4. **배틀 모드의 실시간 요구사항** — 트레이드보다 지연에 민감할 수 있음. Phase 4에서 측정.
5. **GSC(Gen 2)는 NSO GB 앱에서 어떤 프로토콜로 통신하는가?** — GBC 링크 케이블 기반일 것. frlgsim 확장 or 별도 구현 결정.
6. **5인 멀티** — FRLG 무선은 멀티 트레이드 룸 가능. 브리지가 1대의 Switch를 대신하는 구조이므로, 3~5인 연결은 "N-브리지 스타"로 확장 가능한지.

# 부록 A — L1 재설계 평가 (2026-08-20 추가)

> 주인님 요구: ① OS 무관 ② 카드 의존성 없이 동작. 코드 레벨 리서치 결과 기록.

## 핵심 발견 (코드 확인)

**frlg-ldn-trade는 join(참가자) 전용으로 설계되어 있다 — AP 모드 불필요.**

`frlgsim/transport.py` (LiveTransport) 확인 결과:
- `ldn.scan(keys)` → `ldn.ConnectNetworkParam()` → **참가자로 LDN 세션 연결**
- 스위치(게임)가 항상 LDN 호스트(리더)가 되고, PC는 참가자
- 게임 데이터는 LDN 위에서 **UDP :12345 브로드캐스트**로 흐름 (Pia 시스템)
- TX: UDP 소켓(SO_BROADCAST), RX: AF_PACKET raw 소켓 (169.254.x 링크-로컬 인터페이스)
- transport 계층이 이미 추상화되어 있음: `ReplayTransport`(오프라인) / `LiveTransport`(라이브) — **여기에 RemoteTransport 추가가 자연스러운 확장점**

kinnay/LDN `wlan.py` 확인 결과 — 필요한 Wi-Fi 모드:
| 역할 | 필요 모드 |
|---|---|
| 스캔 | monitor (비콘/광고 프레임 수신) |
| 참가 (join) | station (assoc 유지) + monitor (데이터/브로드캐스트 수신) |
| 호스트 (host) | **AP + monitor** ← 우리는 불필요 |

## 요구사항별 평가

### ① "카드 의존성 없이" — ⚠️ 대폭 완화, 거의 충족

- **AP 모드 요구 제거** → 카드 조건이 "station + monitor + 인젝션"으로 완화 (대부분의 리눅스 지원 카드 충족)
- **RTL8188EU (보유 카드)**: aircrack-ng/rtl8188eus 드라이버가 **모니터 모드 + 프레임 인젝션 공식 지원** — 후보로 충분
- LDN 기본 대역 = **2.4GHz (ch 1/6/11)** (NintendoClients 위키 LDN-Protocol 문서) — RTL8188EU(2.4GHz 전용)와 호환
- 남은 리스크: LDN Common Issues #7 (참가 후 브로드캐스트 액션 프레임 드롭) — **카드별 실측 필요** (Intel AX200이 실패한 지점. RTL8188EU는 실측 전까지 미확정)

### ② "OS 무관하게" — ❌ 네이티브는 구조적으로 불가, ⚠️ 계층 분리로 우회

- LDN은 nl80211/netlink 기반 (Linux 전용). 모니터 모드 + radiotap 인젝션은 **macOS 불가, Windows 극히 제한적**
- **해법: 무선 프론트엔드 분리** — L1(무선)만 리눅스 박스가 담당하고, PC(macOS/Windows)는 클라이언트로만 동작

```
[Switch] ⇄무선⇄ [리눅스 프론트엔드 (L1+L2)] ⇄USB/네트워크⇄ [PC 클라이언트 (L3+L4, 아무 OS)]
```

프론트엔드 후보:
| 옵션 | 비용 | 설명 |
|---|---|---|
| **USB 부팅 리눅스** (설치 없음) | 0원 | USB 스틱 하나로 임시 PoC. 매번 부팅 필요 |
| **미니DC (Ubuntu 24.04 예정)** | 0원 | 상시 브리지 머신. RTL8188EU를 USB에 꽂으면 끝. 가장 현실적 |
| Pi Zero 2W + 카드 | ~3만원 | gblink-pro 패턴 — "LDN 동글"로 패키징. 소형/상시 |

## 결론

| 요구 | 평가 |
|---|---|
| OS 무관 | PC 측은 충족 (클라이언트 분리). 무선 계층은 Linux 필수 — **우회로 해결** |
| 카드 무관 | **AP 모드 의존성 제거 확인** → 보유 RTL8188EU로 PoC 시도 가치 충분. 실측으로 검증 |
| 새 리눅스 설치 | 불필요 (USB 부팅 or 미니DC 활용) |
| 새 카드 구매 | **불필요** (RTL8188EU 우선 시도) |

**재설계 방향**: 기존 kinnay/LDN join 경로를 그대로 쓰되 (재작성 불필요), transport 계층에 RemoteTransport를 추가하고, L1을 분리 실행 가능한 프론트엔드 데몬으로 패키징. 실측 1회 (RTL8188EU + USB 부팅 리눅스)로 확정.
