## 0. 한 줄 요약

PC(8192EU)가 여는 FRLG 방의 **비콘은 이제 공중에 정상 송출**된다(100ms 간격, WPA2 PRIVACY 표시).
그러나 **스위치의 방 검색 리스트에는 나타나지 않는다.** 남은 원인은 무선 계층이 아니라
**"스위치가 방을 어떻게 발견하고 리스트에 올리는가"의 프로토콜 계층**에 있다.

## 1. 확정된 사실 (실측 기반)

| # | 사실 | 검증 방법 |
|---|---|---|
| F1 | 비콘 송출 정상 (102개/12s = ~100ms 간격) | VM2 모니터 캡처 |
| F2 | PRIVACY 비트 ON + RSN IE 포함 (capability 0x0431) | tcpdump "ESS CH: 6, PRIVACY" 표시 |
| F3 | comm_id/scene_id는 실제 스위치 것과 바이트 동일 | T1/T4 캡처 대조 |
| F4 | application_data 122B 구조 일치 (D1/D2/D3 반영) | 오프라인 바이트 대조 |
| F5 | 스위치 A·B 양쪽 방 검색에서 미표시 | 주인님 실기 확인 (2회) |
| F6 | ldn-mon에서 스위치의 **Probe Request가 관측되지 않음** | tcpdump 12s — 스위치가 우리 AP를 "보고 있는지" 미확정 |
| F7 | ldn의 LDN 광고는 Vendor Action 프레임(브로드캐스트, 100ms) | ldn-mon 캡처: Action: Vendor Act#0 |

## 2. 핵심 미해결 질문

**Q: 스위치는 우리 방을 "못 보는가(무선 계층)" 아니면 "보지만 버리는가(프로토콜 계층)?**

이것을 먼저 확정해야 수정 방향이 정해진다. 두 시나리오의 수정 경로가 완전히 다르기 때문.

### 시나리오 A: "보지만 버린다" (프로토콜 계층 문제) — 유력
- 비콘은 도달하지만 스위치의 방 리스트 필터에서 탈락
- 후보 원인: ①application_data 파싱 실패 ②comm_id/scene 조건 ③Vendor Action 광고 프레임 부재/불일치 ④보안 협상(assoc) 실패
- **검증 방법**: VM1에서 스위치의 Probe Request/Auth 프레임 관측 → 오면 무선 계층은 통과한 것

### 시나리오 B: "아예 못 본다" (무선 계층 문제) — 가능성 낮음
- 스위치의 passive scan이 우리 비콘을 수신하지 못함
- 후보 원인: ①스위치 스캔 채널 세트에 CH6 없음(불가능, FRLG LDN은 CH6 고정) ②모뎀/RF 물리 이슈
- **검증 방법**: 스위치를 검색 화면에 둔 채 VM1 ldn-mon에서 Probe Request 대기

## 3. 잠재적 원인 & 수정 사항 (우선순위 순)

### P0 — 스위치 관측 확정 (수정 아님, 진단)
**작업**: 스위치 A를 검색 화면에 둔 상태에서 VM1 ldn-mon(또는 VM2)으로
`type mgt subtype probe req` + `type auth`를 60초 캡처.
- **Probe Request가 온다** → 시나리오 A 확정 → P1~P3 진행
- **안 온다** → 시나리오 B → 무선 계층 재검토 (P4)

### P1 — Vendor Action(LDN 광고) 프레임 검증
**가설**: 스위치는 비콘만이 아니라 **ldn Vendor Action 광고 프레임**을 파싱해 방 리스트를 구성한다.
우리는 Action을 뿌리고 있지만(F7), 그 내용물이 스위치가 기대하는 형식과 다를 수 있다.

**작업**:
1. 실제 스위치 방(DESTROY)이 뿌리는 Vendor Action 프레임을 T1/T4 로그·캡처에서 추출
2. 우리가 뿌리는 Action 프레임과 **전체 hex 대조** (beacon application_data 때와 동일한 방법)
3. 차이 발견 시 ldn의 Action 생성 코드(`ldn/__init__.py`의 advertise 부분) 패치

**참고**: Action 프레임은 ldn 내부에서 생성되며 우리가 수정한 beacon head와는 별개 경로다.

### P2 — Auth/Assoc 응답 경로 검증
**가설**: 스위치가 방을 리스트에 올리기 전에 실제 802.11 인증(Auth)을 시도하고,
우리 AP가 응답하지 못하면 리스트에서 제외된다.

**작업**:
1. ldn의 Auth 처리 코드 확인 (`wlan.py`의 auth frame 핸들러)
2. 스위치가 Auth를 보내면 우리가 응답하는지 로그 확인
3. 응답하지 못한다면 → Auth 응답 프레임 생성·송신 경로 디버깅

**주의**: ldn은 `device_ap_sme` 모드로 동작 — 커널이 아니라 **ldn이 직접** Auth/Assoc/Probe에
응답한다. 이 응답이 무선으로 나가는지 별도 확인 필요 (TX 경로가 START_AP와 다를 수 있음)

### P3 — application_data 세부 파싱
**가설**: D2 닉네임 TLV 형식이 정확하지 않아 스위치 파서가 실패한다.
현재 우리 형식: `[0x03][0x01][nickname bytes]` — 'Min'(3글자) 샘플 하나에서 추정한 것.

**작업**:
1. 실제 스위치의 application_data에서 닉네임이 긴 경우(4글자 이상) 샘플 확보
2. TLV 길이 필드의 정확한 의미 확인 (현재 0x01이 길이인지 플래그인지 불명)
3. 필요시 스위치 닉네임을 3글자로 맞춰 테스트

### P4 — (시나리오 B인 경우만) 무선 계층 재검토
- VM2 모니터를 스위치 옆에 두고 스위치의 Probe Request가 공중에 나오는지 확인
- 스위치의 스캔이 active scan이라면 Probe Request가 관측되어야 함

## 4. 권장 작업 순서 (코덱스 지시용)

```
1. [진단] P0: 스위치 관측 여부 확정 (주인님 협조 필요 - 스위치 검색 화면 유지)
2. [분석] P1-1: 실제 스위치 Vendor Action 프레임 확보·디코딩
3. [구현] P1-2: ldn Action 프레임 패치 (필요시)
4. [분석] P2: ldn Auth/Assoc 응답 경로 코드 리딩
5. [구현] P2-2: Auth 응답 수정 (필요시)
6. [검증] 매 단계 VM1 재기동 + VM2 캡처 + 스위치 확인
```
